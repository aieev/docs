<Note>
  Air Job은 비공개 프리뷰입니다. 정식 출시 전에 동작, 제한, 엔드포인트가 바뀔 수 있습니다. 프리뷰 Base URL은 [퀵스타트](/docs/ko/air-job/quickstart)를 참고하세요.
</Note>

Job은 컨테이너 이미지와 명령을 명령이 끝날 때까지 실행한 뒤 GPU를 반납하는 워크로드입니다. 학습, 배치 추론, 데이터 처리, 평가처럼 끝이 있는 작업에 적합합니다. [Air Container](/docs/ko/air-container/index)와 달리 Replica, 포트, 오토스케일링이 없고 실행되는 동안에만 비용이 발생합니다.

## 동작 방식

1. CLI, API, 또는 `job.yaml`로 이미지, 명령, 인스턴스 타입을 지정해 Job을 제출합니다.
2. AirCloud가 Job을 대기열에 등록하고 GPU 자원을 기다립니다.
3. 컨테이너가 시작되고 명령이 실행됩니다. 실행 중에 `stdout`과 `stderr`를 실시간으로 볼 수 있습니다.
4. 명령이 종료되면 Job이 `SUCCEEDED` 또는 `FAILED`로 끝나고 exit code가 기록됩니다.

## 사전 준비

- 프로젝트의 API Key. [인증](/docs/ko/get-started/authentication)을 참고하세요.
- 영구 데이터를 읽고 써야 한다면 볼륨. 현재는 같은 프로젝트의 Endpoint에 붙어 있는 기존 볼륨을 Job이 마운트합니다.
- 조직에 충분한 크레딧. 선불 조직은 잔액이 소진되면 Job이 취소됩니다.
- CLI를 사용한다면 `aircloud` CLI 0.3.0 이상

## 상태 흐름

```text
QUEUED -> PENDING -> STARTING -> RUNNING -> SUCCEEDED
                                         -> FAILED
진행 중인 모든 상태 -> CANCELLING -> CANCELLED
```

| 상태 | 의미 |
| --- | --- |
| `QUEUED` | Job이 접수되었습니다. |
| `PENDING` | GPU 자원을 기다리는 중입니다. |
| `STARTING` | 이미지를 가져오고 컨테이너를 시작하는 중입니다. |
| `RUNNING` | 명령이 실행 중입니다. |
| `SUCCEEDED` | 명령이 exit code 0으로 종료되었습니다. |
| `FAILED` | Job이 실패했습니다. `reason`을 확인하세요. |
| `CANCELLING` / `CANCELLED` | 취소 요청이 접수된 뒤 완료되었습니다. |

`FAILED`와 `CANCELLED` Job은 `reason`으로 사유를 확인할 수 있습니다.

`message`는 `reason`에서 파생된 사람이 읽을 수 있는 고정 설명이며(영어 문자열), Job이 실행 중이거나 `reason`이 없으면 `null`입니다. 플랫폼이 Job 상태를 일시적으로 확인하지 못하면 `status_unknown_since`가 설정되고 `message`에 자동으로 다시 확인한다는 안내가 표시됩니다.

`IMAGE_PULL`, `COMMAND_INVALID`, `VOLUME_ERROR`일 때는 Job과 `attempts`의 각 항목에 있는 `detail`이 실제 오류를 정제한 발췌(최대 500자)를 보여 줍니다. `PENDING`이나 `QUEUED` 상태(취소 중이 아닐 때)에서는 GPU 자원을 기다리는 중이며 15분 안에 자원을 받지 못하면 `CAPACITY_TIMEOUT`으로 실패한다는 고정 안내가 들어 있습니다. 그 밖에는 `null`입니다.

| Reason | 의미 |
| --- | --- |
| `USER_EXIT_NONZERO` | 명령이 0이 아닌 코드로 종료되었습니다. `exit_code`를 확인하세요. 종료 코드 129~159는 프로세스가 시그널로 종료되었음을 뜻하며(코드 − 128), 예를 들어 `137`은 `SIGKILL`, `143`은 `SIGTERM`입니다. |
| `OOM` | 컨테이너 메모리가 부족했습니다. |
| `IMAGE_PULL` | 이미지를 가져오지 못했습니다. 이미지 URL과 레지스트리 자격 증명을 확인하세요. |
| `COMMAND_INVALID` | 명령을 시작할 수 없습니다. 잘못된 명령, 없는 실행 파일, 노드와 맞지 않는 이미지 아키텍처 등이 원인입니다. 컨테이너가 시작되지 않았습니다. |
| `TIMEOUT` | `timeout_seconds`를 넘겨 Job이 중지되었습니다. |
| `CAPACITY_TIMEOUT` | 자원을 900초 넘게 기다렸습니다. `timeout_seconds`와는 무관합니다. 나중에 다시 제출하거나 다른 인스턴스 타입을 선택하세요. |
| `PLATFORM_ERROR` / `PLATFORM_LOST` | 인프라 장애입니다. `max_retries`를 지정하면 자동으로 다시 실행하며([재시도](#재시도) 참고), 지정하지 않았다면 다시 제출하세요. |
| `VOLUME_ERROR` | Job에 볼륨을 연결하지 못했습니다. 볼륨 상태를 확인하고, 계속되면 지원팀에 문의하세요. |
| `USER_CANCELLED` | 사용자가 취소했습니다. |
| `BALANCE_EXHAUSTED` | 선불 잔액이 소진되어 Job이 취소되었습니다. |

## command와 args

`command`와 `args` 중 하나는 반드시 지정해야 하며, 둘 다 없으면 `422`를 반환합니다.

- `command`는 이미지의 `ENTRYPOINT`를 대체합니다. 지정한 명령이 PID 1이 되고 `ENTRYPOINT`의 초기 설정은 건너뜁니다. NGC와 공식 PyTorch 이미지는 `command`로 문제없이 동작합니다.
- `args`는 이미지의 `CMD`를 대체하며 이미지 `ENTRYPOINT`에 전달됩니다. conda 환경 활성화나 사용자 전환처럼 `ENTRYPOINT`가 필요한 초기 설정을 수행할 때만 사용하세요.
- `ENTRYPOINT`가 도구 자체인 이미지(`curlimages/curl`, `amazon/aws-cli`, `alpine/git` 등)에서 `docker run <이미지> --version`처럼 인자만 넘기려면 `args: ["--version"]`을 사용하세요. `command: ["--version"]`은 `--version`이라는 실행 파일을 찾다가 `COMMAND_INVALID`로 실패합니다.

## 취소와 종료 시그널

취소하거나 `timeout_seconds`가 지나면 컨테이너의 PID 1에 `SIGTERM`을 보내고, 30초 안에 끝나지 않으면 `SIGKILL`로 종료합니다.

- `command`로 실행한 프로세스는 PID 1이 됩니다. PID 1은 시그널 핸들러를 직접 등록하지 않으면 `SIGTERM`을 무시하므로, 핸들러가 없는 `sleep`이나 학습 스크립트는 30초를 다 채운 뒤 강제 종료됩니다.
- 체크포인트 저장처럼 종료 전에 할 일이 있다면 `SIGTERM` 핸들러를 등록하세요(셸은 `trap`, Python은 `signal.signal(signal.SIGTERM, ...)`). 핸들러가 있으면 수 초 안에 종료되고, 핸들러가 출력한 로그도 남습니다.
- 셸 스크립트로 감싸 실행한다면 마지막 명령을 `exec`로 실행해 시그널이 그 프로세스에 바로 전달되게 하세요.

## 타임아웃

`timeout_seconds`는 선택 항목이며 attempt마다 적용되는 실행 시간 제한입니다. 60초 이상 2147483647초 이하로 지정하고(실질적 상한 없음), 기본값 `null`은 제한 없음입니다.

- 컨테이너가 시작된 시점부터 측정합니다. 이미지 pull과 대기열 대기 시간은 포함하지 않습니다.
- 제한 시간이 지나면 `SIGTERM`을 보내고 30초 뒤 `SIGKILL`로 종료합니다. Job은 reason `TIMEOUT`으로 `FAILED`가 됩니다.
- 중지된 시점까지 과금됩니다.

## 재시도

기본적으로 Job은 재시도하지 않습니다. `max_retries`(0~10의 정수, 기본 0)를 지정하면 취소를 제외한 모든 실패 뒤에 그 횟수만큼 추가로 다시 실행합니다. CLI에서는 `--retries`를 사용합니다.

- 취소를 제외한 모든 실패를 `reason`과 관계없이 `max_retries` 횟수가 남아 있는 동안 다시 실행합니다. 취소된 Job은 재시도하지 않습니다.
- 재실행 사이에는 Job이 `QUEUED` 상태로 돌아갑니다.
- 재시도는 즉시가 아니라 약 1분 안에 다시 제출됩니다. `PLATFORM_LOST`와 종료 코드가 없는 실패는 이전 컨테이너가 중지될 수 있도록 먼저 약 3분 기다립니다.
- attempt마다 `timeout_seconds`가 새로 적용됩니다.
- 모든 attempt가 과금됩니다.

- `attempt`는 현재 attempt 번호입니다(1부터 시작).
- `attempts`는 종료된 attempt의 `status`, `reason`, `exit_code`, `started_at`, `finished_at` 이력입니다.
- 컨테이너에는 `AIRCLOUD_JOB_ID`, `AIRCLOUD_ATTEMPT` 환경 변수가 주입됩니다. `env`에 같은 이름을 지정해도 플랫폼 값이 우선합니다.

## 로그

Job이 실행되는 동안이나 끝난 뒤에 `stdout`과 `stderr`를 조회할 수 있습니다. 출력 스트림, 검색어, 시간 범위로 필터링하고 페이지 단위로 가져올 수 있습니다. 기본값은 시작된 가장 최근 attempt이며, 이전 attempt는 `attempt`로 지정하세요. CLI의 `--follow`는 Job이 끝날 때까지 로그를 스트리밍합니다.

- 로그는 최신 줄부터 반환됩니다. 시간순으로 읽으려면 받은 순서를 뒤집으세요.
- 같은 밀리초 안에 출력된 줄의 순서는 보장되지 않습니다.
- 출력된 줄이 조회되기까지 수십 초 걸릴 수 있습니다.
- 16KB를 넘는 줄도 한 레코드로 저장됩니다. 아주 긴 줄은 여러 레코드로 나뉘어 저장될 수 있습니다.
- 줄바꿈 없이 끝난 마지막 출력도 마지막 줄로 수집됩니다.

## 실행 환경

- CPU와 메모리 한도는 인스턴스 타입대로 컨테이너에 적용됩니다. 다만 `nproc`, `os.cpu_count()`, `/proc/meminfo`는 컨테이너 한도가 아니라 노드 전체 값을 보여 줍니다. 데이터로더 워커 수나 스레드 수는 인스턴스 타입의 vCPU 수에 맞춰 직접 지정하세요.
- 컨테이너 파일 시스템의 내용은 Job이 끝나면 사라집니다. 남겨야 할 결과는 마운트한 볼륨에 저장하세요.
- 프로세스는 이미지에 지정된 사용자로 실행되며, 지정이 없으면 `root`입니다.
- RTX 5090(Blackwell, `sm_120`)은 CUDA 12.8 이상으로 빌드된 프레임워크가 필요합니다. PyTorch는 2.7 이상의 CUDA 12.8 빌드를 사용하세요. 그보다 오래된 이미지는 GPU를 인식하지 못하거나 커널 실행 시 실패합니다.

## 사용량과 비용

Air Container와 같은 방식으로 과금합니다. 금액 단위는 KRW입니다.

- 실행 구간이 걸친 10분 단위 구간(정각 기준 :00, :10, :20 …)마다 과금합니다. 최소 10분이며, 짧은 Job이라도 구간 경계를 넘으면 두 구간이 과금됩니다.
- GPU 자원을 확보하지 못해 기다리는 동안은 과금되지 않습니다. GPU가 배정된 뒤부터는 이미지를 가져오는 시간도 포함되며, 이미지나 명령 오류로 컨테이너가 시작되지 못한 경우에도 해당 구간이 과금됩니다.
- 재시도한 attempt는 각각 과금됩니다. 같은 10분 구간 안에서 다시 실행되면 한 번만 과금됩니다.
- 사용량은 Job이 끝나고 약 10분 뒤에 조회됩니다.

- `amount`는 청구가 확정된 금액입니다.
- `pending_amount`는 아직 청구되지 않은 구간의 예상 금액이며 실제 청구액보다 클 수 있습니다.

Job 한 건은 Job 사용량 엔드포인트에서 10분 구간별 내역과 함께, 프로젝트 전체는 프로젝트 사용량 엔드포인트에서 Job별 합계를 기간별로(기본 최근 30일, 최대 92일) 조회합니다. 조직 잔액과 거래 내역은 프로젝트 API Key로 조회할 수 없으며 콘솔에서 확인합니다.

## 중복 제출 방지

제출 요청마다 `Idempotency-Key` 헤더를 보내세요.

- 사용자가 제출할 때마다 새 키(UUID 권장)를 만들고, 타임아웃이나 네트워크 오류로 같은 요청을 재시도할 때는 같은 키를 사용합니다.
- 같은 키와 같은 본문이면 새 Job을 만들지 않고 처음 Job을 반환합니다. 응답에 `Idempotent-Replayed: true` 헤더가 포함됩니다.
- 같은 키에 다른 본문이면 `422`를 반환합니다.
- 키는 프로젝트 단위로 24시간 유지됩니다. 키가 없으면 요청마다 새 Job이 생성됩니다.

CLI는 제출마다 키를 자동으로 붙이고, 재시도할 때도 같은 키를 사용합니다.

## 제한 사항

- 기본적으로 최대 실행 시간이 없습니다. `timeout_seconds`로 attempt별 제한을 걸 수 있으며, 지정하지 않으면 명령이 끝나거나, 직접 취소하거나, 선불 잔액이 소진될 때까지 실행됩니다.
- Job당 볼륨은 1개만 마운트할 수 있습니다. 마운트 경로는 `/`가 아닌 절대 경로여야 하며 서로 겹칠 수 없습니다.
- 이름은 100자, 환경 변수는 100개(키와 값 합계 32KB), `command`와 `args`는 합계 64KB까지 지정할 수 있습니다.
- `command`는 이미지의 `ENTRYPOINT`를, `args`는 이미지의 `CMD`를 대체합니다. [command와 args](#command와-args)를 참고하세요.
- 실패한 Job은 `max_retries`(최대 10)를 지정하지 않으면 재시도하지 않으며, 지정하면 취소를 제외한 모든 실패를 그 횟수만큼 다시 실행합니다. [재시도](#재시도)를 참고하세요.
- API로 결과 파일을 내려받는 기능은 아직 없습니다. 결과는 마운트한 볼륨에 저장하세요.
