A Job runs a container image with a command until the command exits, then releases its GPU. Use it for work that has an end: training, batch inference, data processing, or evaluation. Unlike [Air Container](/docs/air-container/index), a Job has no Replicas, ports, or Autoscaling, and you pay only while it runs.

## How it works

1. You submit a Job with an image, a command (or args), and an instance type, using the CLI, the API, or a `job.yaml` file.
2. AirCloud queues the Job and waits for GPU capacity.
3. The container starts and runs your command. You can stream `stdout` and `stderr` while it runs.
4. When the command exits, the Job ends with `SUCCEEDED` or `FAILED`, and its exit code is recorded.

## Prerequisites

- An API key for the project. See [Authentication](/docs/get-started/authentication).
- A volume if your Job reads or writes persistent data. Today a Job mounts an existing volume that is attached to an Endpoint in the same project.
- Enough credits in your organization. Prepaid organizations are cancelled when the balance runs out.
- The `aircloud` CLI version 0.3.0 or later, if you use the CLI.

## Status lifecycle

```text
QUEUED -> PENDING -> STARTING -> RUNNING -> SUCCEEDED
                                         -> FAILED
any active status -> CANCELLING -> CANCELLED
```

| Status | Meaning |
| --- | --- |
| `QUEUED` | The Job was accepted. |
| `PENDING` | Waiting for GPU capacity. |
| `STARTING` | Pulling the image and starting the container. |
| `RUNNING` | Your command is running. |
| `SUCCEEDED` | The command exited with code 0. |
| `FAILED` | The Job failed. See `reason`. |
| `CANCELLING` / `CANCELLED` | A cancel request was accepted, then completed. |

For `FAILED` and `CANCELLED` Jobs, `reason` tells you why.

`message` is a fixed, human-readable explanation derived from `reason`. For `IMAGE_PULL`, `COMMAND_INVALID` and `VOLUME_ERROR`, `detail` (on the Job and on each entry of `attempts`) adds a sanitized excerpt of the underlying error, up to 500 characters. While the Job is `PENDING` or `QUEUED` (and not being cancelled), `detail` is a fixed notice that it is waiting for GPU capacity and fails with `CAPACITY_TIMEOUT` if none becomes available within 15 minutes. In every other case it is `null`. If the platform temporarily cannot confirm the Job's state, `status_unknown_since` is set and `message` says it will be rechecked automatically.

| Reason | Meaning |
| --- | --- |
| `USER_EXIT_NONZERO` | Your command exited with a non-zero code. See `exit_code`. Exit codes 129-159 mean the process was killed by a signal (code minus 128), for example `137` = `SIGKILL` and `143` = `SIGTERM`. |
| `OOM` | The container ran out of memory. |
| `IMAGE_PULL` | The image could not be pulled. Check the image URL and registry credentials. |
| `COMMAND_INVALID` | The command could not be started: a bad command, a missing executable, or an image that does not match the node architecture. The container never started. |
| `TIMEOUT` | The Job exceeded `timeout_seconds` and was stopped. |
| `CAPACITY_TIMEOUT` | The Job waited more than 900 seconds for capacity. This is unrelated to `timeout_seconds`. Submit again later or choose another instance type. |
| `PLATFORM_ERROR` / `PLATFORM_LOST` | Infrastructure failure. Set `max_retries` to retry automatically (see [Retries](#retries)), or submit the Job again. |
| `VOLUME_ERROR` | The volume could not be attached to the Job. Check the volume's state, or contact support if it keeps happening. Not retried by default. |
| `USER_CANCELLED` | You cancelled the Job. |
| `BALANCE_EXHAUSTED` | The prepaid balance ran out and the Job was cancelled. |

## Command and args

Set at least one of `command` and `args`; a request with neither returns `422`.

- `command` replaces the image `ENTRYPOINT`. Your command becomes PID 1 and any setup the `ENTRYPOINT` performs is skipped. NGC and official PyTorch images work fine with `command`.
- `args` replaces the image `CMD` and is passed to the image `ENTRYPOINT`. Use it only when the `ENTRYPOINT` does setup you need, such as activating a conda environment or switching users.
- For images whose `ENTRYPOINT` is the tool itself (`curlimages/curl`, `amazon/aws-cli`, `alpine/git`, …), pass arguments the way you would with `docker run <image> --version` by using `args: ["--version"]`. `command: ["--version"]` looks for an executable named `--version` and fails with `COMMAND_INVALID`.

## Cancellation and stop signal

When you cancel a Job or `timeout_seconds` expires, the platform sends `SIGTERM` to PID 1 in the container and kills it with `SIGKILL` if it has not exited within 30 seconds.

- A process started with `command` runs as PID 1. PID 1 ignores `SIGTERM` unless it installs a handler, so a plain `sleep` or a training script without one is killed only after the full 30 seconds.
- If you need to save a checkpoint or clean up before exiting, install a `SIGTERM` handler (`trap` in a shell, `signal.signal(signal.SIGTERM, ...)` in Python). With a handler the Job stops within seconds and the handler's output stays in the logs.
- If you wrap your program in a shell script, start the last command with `exec` so the signal reaches it directly.

## Timeout

`timeout_seconds` is optional. It is the run time limit for each attempt, from 60 up to 2147483647 seconds (no practical cap). `null`, the default, means no limit.

- The clock starts when the container starts. Image pull and queue wait are not counted.
- On expiry the platform sends `SIGTERM`, then `SIGKILL` after 30 seconds. The Job ends `FAILED` with reason `TIMEOUT`.
- You are billed up to the time the Job stops.

## Retries

Jobs are not retried by default. Set `max_retries` (an integer from 0 to 10, default 0) to run up to that many additional attempts after a failed one.

- A failed attempt is retried only if its `reason` is in `retry_on` and attempts remain under `max_retries`. Cancelled Jobs are not retried.
- `retry_on` defaults to `["PLATFORM_ERROR", "PLATFORM_LOST"]`, so by default only infrastructure failures are retried. Allowed values: `USER_EXIT_NONZERO`, `OOM`, `IMAGE_PULL`, `COMMAND_INVALID`, `TIMEOUT`, `CAPACITY_TIMEOUT`, `PLATFORM_ERROR`, `PLATFORM_LOST`, `VOLUME_ERROR`.
- To retry failures caused by your code, such as `USER_EXIT_NONZERO` or `OOM`, list them explicitly, for example `"max_retries": 2, "retry_on": ["PLATFORM_ERROR", "PLATFORM_LOST", "OOM"]`. With the CLI, use `--retries 2 --retry-on PLATFORM_ERROR,PLATFORM_LOST,OOM`. The value replaces the default, so include the platform reasons if you still want them retried.
- The response returns the `retry_on` in effect as `spec.retry_on`.
- The Job returns to `QUEUED` between attempts.
- The platform checks for Jobs waiting to retry about once a minute, so a retry is resubmitted within about a minute rather than instantly. Failures with an exit code are resubmitted at the next check; `PLATFORM_LOST` and failures without an exit code wait about 3 minutes first so the previous container can stop.
- Each attempt gets a fresh `timeout_seconds`.
- All attempts are billed.

- `attempt` is the current attempt number, starting at 1.
- `attempts` lists the finished attempts with their `status`, `reason`, `exit_code`, `started_at`, and `finished_at`.
- Your container receives the environment variables `AIRCLOUD_JOB_ID` and `AIRCLOUD_ATTEMPT`. If you set variables with the same names in `env`, the platform values take precedence.

## Logs

Read `stdout` and `stderr` while the Job runs or after it ends. You can filter by source, search text, or time range, and page through results. By default you get the latest attempt that started; pass `attempt` to read an earlier one. With the CLI, `--follow` streams logs until the Job finishes.

- Logs are returned newest first. Reverse them to read in time order.
- Lines printed within the same millisecond have no guaranteed order.
- A line can take tens of seconds to become visible.
- A line longer than 16 KB is still stored as one record. A very long line can be split across several records.
- Output that ends without a trailing newline is collected as the last line.

## Execution environment

- CPU and memory limits match the instance type and are enforced on the container. However, `nproc`, `os.cpu_count()` and `/proc/meminfo` report the whole node, not the container limit. Set data loader workers and thread counts from the instance type's vCPU count yourself.
- Anything written to the container file system is gone when the Job ends. Write results you want to keep to a mounted volume.
- Processes run as the user the image specifies, or `root` if it specifies none.
- RTX 5090 (Blackwell, `sm_120`) needs frameworks built with CUDA 12.8 or later. For PyTorch, use a CUDA 12.8 build of 2.7 or later. Older images either do not see the GPU or fail when launching kernels.

## Usage and cost

Jobs are billed the same way as Air Container. Amounts are in KRW.

- You are billed for every 10-minute interval (aligned to :00, :10, :20, …) that the run overlaps. The minimum is 10 minutes, and even a short Job is billed for two intervals if it crosses a boundary.
- Time spent waiting because no GPU is available is not billed. Once a GPU is assigned, image pull time counts, and the interval is billed even if the container never starts because of an image or command error.
- Each retried attempt is billed. Attempts that run within the same 10-minute interval are billed once.
- Usage becomes visible about 10 minutes after the Job ends.

- `amount` is the confirmed charge.
- `pending_amount` is an estimate for intervals that have not been charged yet. It can be higher than the final charge.

Use the Job usage endpoint for one Job, with a breakdown by 10-minute interval, or the project usage endpoint for totals per Job over a date range (default last 30 days, up to 92 days). Organization balance and transactions are shown in the console, not through a project API key.

## Avoid duplicate submissions

Send an `Idempotency-Key` header with every submit request.

- Create a new key (a UUID works well) for each user submit action, and reuse the same key when you retry that request after a timeout or network error.
- The same key with the same body returns the original Job and creates nothing new. The response includes `Idempotent-Replayed: true`.
- The same key with a different body returns `422`.
- Keys are kept for 24 hours per project. Without a key, every request creates a new Job.

The CLI adds a key to every submission and retries with the same key automatically.

## Limits and behavior

- By default there is no maximum run time. Set `timeout_seconds` to limit each attempt; otherwise a Job runs until its command exits, you cancel it, or the prepaid balance is exhausted.
- A Job can mount one volume. Mount paths must be absolute, must not be `/`, and must not repeat.
- Names can be up to 100 characters, environment variables up to 100 (32 KB for keys and values combined), and `command` plus `args` up to 64 KB in total.
- `command` replaces the image `ENTRYPOINT` and `args` replaces the image `CMD`. See [Command and args](#command-and-args).
- Failed Jobs are not retried unless you set `max_retries` (up to 10), and only for the reasons in `retry_on` (default: platform failures). See [Retries](#retries).
- Downloading result files through the API is not available yet. Write results to a mounted volume.
